# Mixture of Experts: Scaling Without Proportional Compute

<Callout type="tip" title="Key Insight">
A dense transformer uses every parameter for every token. Mixture of Experts breaks the feedforward layers into many specialized experts and activates only a few per token. A 671B MoE model (DeepSeek-V3) with 37B active parameters does the same FLOPs per token as a 37B dense model — but has the representation capacity of a 671B model. You pay dense compute, you get large-model quality.
</Callout>

## The Dense Model Problem

In a standard transformer, the feedforward layer has parameters $W_1 \in \mathbb{R}^{d \times 4d}$ and $W_2 \in \mathbb{R}^{4d \times d}$. Every token, at every layer, multiplies through both matrices. Doubling the hidden dimension quadruples the FFN parameters and the FLOPs.

**Scaling hypothesis**: more parameters → better models. But more parameters also means more compute per forward pass. At some scale, the compute becomes the bottleneck — you can't afford to run inference on a 10T dense parameter model, no matter how good it is.

MoE breaks this coupling: parameters and compute can grow independently.

## The MoE Architecture

Replace each dense feedforward layer with $N$ expert networks, each identical in structure to the original FFN:

$$\text{MoE}(x) = \sum_{i=1}^{N} G_i(x) \cdot E_i(x)$$

Where $E_i(x)$ is the $i$-th expert's output and $G_i(x)$ is a gating weight. The gating network is a simple linear projection followed by softmax:

$$G(x) = \text{Softmax}(\text{TopK}(x W_g, k))$$

**TopK gating**: only the top-$k$ experts (by gating score) are computed. The gating weights of all other experts are set to zero — those experts don't run. If $N=256$ and $k=8$: 8 experts run, 248 don't. Compute scales with $k$, not $N$.

## Load Balancing: The Core Challenge

A naive implementation collapses: the gating network learns to route most tokens to a few "popular" experts, leaving the rest idle. This defeats the purpose of having many experts.

**Auxiliary load balancing loss** (introduced in Switch Transformer, Fedus et al., 2021) adds a penalty for uneven expert utilization:

$$\mathcal{L}_{\text{aux}} = \alpha \sum_{i=1}^{N} f_i \cdot p_i$$

Where $f_i$ is the fraction of tokens routed to expert $i$, and $p_i$ is the average routing probability to expert $i$. This term is minimized when all experts receive equal traffic — it penalizes any expert receiving more than its fair share.

**Expert capacity**: each expert processes at most $C$ tokens per batch (capacity factor $\times$ batch\_size / N). Tokens that overflow the capacity limit are dropped (or routed to a shared expert). This bounds the per-expert compute regardless of routing choices.

**DeepSeek's fine-grained routing** (DeepSeek-V2, 2024): instead of $N=8$ large experts, use $N=64$ small experts with $k=8$ selected. Each expert is a smaller network. Fine-grained routing reduces the variance in each expert's specialization and distributes knowledge more evenly.

## GShard and Switch Transformer

**GShard (Lepikhin et al., Google, 2021)** was the first paper to scale MoE to 600B parameters (600B total, 96B active). Key contributions: top-2 gating, expert capacity with token dropping, and efficient shard-parallel training across 2048 TPUs.

**Switch Transformer (Fedus et al., Google, 2021)** simplified to top-1 gating (one expert per token) and showed this outperforms top-2 for the same FLOP budget. Key finding: switching to MoE with the same training compute as T5-Base (top-1, 8 experts) achieves 7× pre-training speed-up. The Switch Transformer with 1.6T parameters achieves T5-XXL quality at 1/7th the training time.

The practical insight: MoE isn't just for making models bigger. At equal compute cost, MoE is faster to train and achieves better quality than dense models.

## Mixtral 8×7B: The Open-Source MoE Moment

**Mixtral 8×7B (Mistral AI, 2023)** brought MoE to the open-source community. Architecture: 8 FFN experts per layer, top-2 routing, 7B parameters per expert (same size as Mistral-7B). Total parameters: 47B. Active parameters per token: 13B (two 7B experts sharing the residual stream, but the non-FFN parameters are shared across all routing paths).

Mixtral 8×7B outperformed Llama-2-70B (5× more active parameters) on most benchmarks. The inference cost is comparable to a 13B dense model (13B active parameters vs 70B for Llama-2-70B). Quality like a 70B model, cost like a 13B model.

**Mixtral 8×22B**: 141B total, 39B active. Competes with GPT-3.5 and Claude Instant at 30–40% lower inference cost.

<Callout type="info" title="Expert Specialization: What Experts Actually Learn">
Sparse experts don't visibly specialize in human-understandable concepts like "expert 3 handles math, expert 7 handles code." Routing patterns show soft specialization by token type and syntactic position, but analysis of what each expert "knows" remains an open research area. What experts clearly do: different experts have different activation patterns for different tokens, and routing is not random — tokens with similar representations tend to route to the same experts. The specialization is real but not interpretable in simple terms.
</Callout>

## DeepSeek-V2 and V3: MoE at Production Scale

**DeepSeek-V2 (2024)** introduced two key innovations beyond standard MoE:

**Shared experts**: 2 experts are always active (shared across all tokens), plus top-$k$ routed experts. Shared experts handle common, general-purpose computation; routed experts handle specialized patterns. This reduces the burden on the load balancing mechanism — common patterns don't compete with specialized ones.

**Fine-grained expert decomposition**: instead of 8 large experts, use 64 small experts (each 1/8 the size) with $k=6$ selected. Same total active parameters, but more diverse routing — any given token can mix from 64 possible specialists rather than 8.

**DeepSeek-V3 (2024)**: 671B total parameters, 37B active. 256 routed experts + 1 shared expert. Trained on 14.8T tokens. FP8 mixed-precision training. At $6M training cost (vs estimated $100M+ for GPT-4), it achieves comparable or better performance on coding, math, and reasoning benchmarks.

The load balancing strategy: auxiliary-loss-free. Instead of adding a loss term, DeepSeek-V3 uses an engineered bias term added to gating logits that is updated after each batch to encourage equal expert utilization. This avoids the quality degradation from adding a competing auxiliary loss.

## Expert Parallelism for Training

MoE adds a new parallelism dimension: **Expert Parallelism (EP)**. Each GPU hosts a subset of experts:
- GPU 0: experts 0–31
- GPU 1: experts 32–63
- ...

During the forward pass: tokens are routed by the gating network, then dispatched to the appropriate GPU (All-to-All communication). Each GPU runs its local experts on the tokens assigned to them. Results are collected back (another All-to-All). 

For DeepSeek-V3 with 256 experts across 32 GPUs: 8 experts per GPU. Each All-to-All communication transfers the activations for a fraction of the batch. This All-to-All overhead is the main cost of MoE training — it scales as $O(\text{batch} \times d_{\text{model}})$ per MoE layer.

## Practice

<Callout type="info">
The most educational MoE experiment: implement a 4-expert MoE FFN layer in PyTorch (4 linear layers + a gating network that selects top-2), train on any language modeling task, and log the routing statistics every 100 steps. Watch the load balancing collapse happen in real time — without the auxiliary loss, one or two experts quickly capture 80%+ of the traffic. Then add the auxiliary loss and watch the routing equalize. The collapse experiment takes 10 minutes and makes the problem immediately concrete.
</Callout>
