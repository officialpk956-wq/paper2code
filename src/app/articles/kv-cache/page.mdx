# The KV Cache: Accelerating LLM Inference

<Callout type="tip" title="Key Insight">
Autoregressive LLMs generate text one token at a time. Without a KV Cache, the model would recompute the attention scores for the entire conversation history during every single token generation, resulting in exponential latency. The KV Cache trades memory for compute, saving past calculations to make generation $O(1)$ instead of $O(N^2)$.
</Callout>

## Mechanics of the KV Cache

In a Transformer, the Self-Attention mechanism requires multiplying three matrices: Queries (Q), Keys (K), and Values (V). 

When generating the 100th token, the model needs to compare the current token's Query against the Keys and Values of all 99 previous tokens. Since those 99 previous tokens haven't changed, their K and V matrices haven't changed either. 

The **KV Cache** simply stores the K and V matrices for all previous tokens in GPU RAM. When generating the next token, the model only computes the Q, K, and V for the *new* token, appends the new K and V to the cache, and computes attention using the cached history.

## The Memory Math

The KV Cache is massive. It grows linearly with every token generated. 

For a standard model, the size of the KV cache for a single token is calculated as:
`2 (for K and V) × Layers × Heads × Head_Dimension × Precision_Bytes`

For a model like **Llama-2 70B** (80 layers, 64 heads, 128 head dim) running in FP16 (2 bytes):
`2 × 80 × 64 × 128 × 2 = 2.62 Megabytes per token per user`.

If a user submits a prompt with 4,000 tokens, storing their KV Cache requires **~10.5 GB of VRAM**. If you want to serve a batch of 10 users simultaneously, you need 105 GB of VRAM *just for the cache*, completely separate from the weights of the model itself. This is why LLM serving is overwhelmingly bottlenecked by Memory Bandwidth, not Compute.

## Multi-Query and Grouped-Query Attention

To reduce the crippling size of the KV Cache, researchers altered the Transformer architecture:
- **Multi-Query Attention (MQA):** Instead of every Query head having its own Key and Value head, MQA forces all Query heads to share a *single* Key and Value head. This shrinks the KV cache size by a factor of the number of heads (e.g., 64x smaller), but can degrade accuracy.
- **Grouped-Query Attention (GQA):** The compromise used in models like Llama-3 and Mistral. Query heads are divided into groups (e.g., 8 groups), and each group shares a single K and V head. This provides significant KV cache compression with almost zero loss in model quality.

## PagedAttention (vLLM)

In a traditional serving engine, memory for the KV Cache is allocated in large, contiguous chunks based on the *maximum possible* sequence length. Because most requests are much shorter than the maximum length, this leads to massive internal fragmentation, wasting up to 60% of GPU memory.

**PagedAttention**, introduced by the vLLM project, borrows the concept of virtual memory and paging from operating systems. It breaks the KV cache down into small, fixed-size blocks (e.g., 16 tokens per block). These blocks are allocated dynamically on-demand and can be stored non-contiguously in VRAM. 

This simple OS-level trick eliminated fragmentation, allowing servers to increase their batch sizes by up to 4x, drastically increasing throughput.

Time how long it takes to generate 500 tokens in both scenarios to physically feel the O(N^2) latency impact of disabling the KV Cache.
