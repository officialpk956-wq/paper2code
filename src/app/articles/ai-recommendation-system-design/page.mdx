# AI Recommendation System Design

<Callout type="tip" title="Key Insight">
Recommendation systems are the engines of the engagement economy. Designing them at scale requires orchestrating real-time streaming data, massive offline feature generation, and sub-100ms multi-stage model inference pipelines.
</Callout>

## The Data Foundation: Feature Stores

A recommendation model is only as good as the context it receives. That context is managed by a **Feature Store**.
- **Offline Features:** Deep, historical data calculated via massive batch jobs (e.g., Apache Spark). Examples include "User's 30-day click-through rate" or "Item's historical purchase frequency."
- **Online Features:** Real-time context processed via streaming pipelines (e.g., Kafka + Flink). Examples include "User's last 5 clicks in the current session" or "Current time of day."

When a user requests the homepage, the backend queries the fast Online Feature Store (backed by Redis or Cassandra) to instantly fetch their profile.

## The Multi-Stage Funnel

You cannot run a heavy neural network on 10 million products in 50 milliseconds. Therefore, recommendation systems are designed as a funnel:

1. **Candidate Generation (Retrieval):** The goal is to narrow 10 million items down to 1,000. This is done using highly efficient models like the **Two-Tower architecture** or Collaborative Filtering matrix factorization. The results from multiple candidate generators (e.g., "Trending items", "Similar to past purchases", "New releases") are combined.
2. **Scoring and Ranking:** The 1,000 candidates are passed to a heavy scoring model (like **Wide & Deep** or **DLRM**). This model looks at the deep interactions between the user's features and the items' features to predict the exact probability of a click or purchase.
3. **Filtering and Business Logic:** The sorted list is passed through hard business rules. (e.g., "Remove items the user already bought," "Ensure at least 20% of the feed is from new creators," "Remove out-of-stock items").

## Real-Time vs Batch Scoring

Different platforms require different scoring architectures:
- **Batch (Pre-computed) Recommendations:** A cron job runs every night, scores items for every user, and saves the top 100 list to a database. Fast, but unresponsive to immediate user actions (like a user suddenly searching for "running shoes"). Used for daily email campaigns.
- **Real-Time Scoring:** The model runs inference the moment the user opens the app, utilizing their most recent clicks. Requires expensive GPU inference clusters but drives massive engagement (the TikTok approach).

## A/B Testing and Shadow Mode

Recommendation models are evaluated in production using rigorous **A/B Testing**. 
Before a new model is fully deployed, it is run in **Shadow Mode**—it receives live traffic and generates recommendations, but its results are thrown away. Engineers monitor its latency and error rates. Once it passes, it is rolled out to 1% of users, and business metrics (like session length or revenue) are tracked against the control group.
