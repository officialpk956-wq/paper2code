# LLM Inference Optimization: KV Cache, vLLM, and Speculative Decoding

<Callout type="tip" title="Key Insight">
LLM inference has two distinct phases: prefill (processing the input prompt in parallel, compute-bound) and decode (generating output tokens one at a time, memory-bandwidth-bound). These two phases have different bottlenecks and different optimization strategies. Most production serving improvements — continuous batching, PagedAttention, speculative decoding — exist because people treated these phases differently.
</Callout>

## The Two-Phase Problem

**Prefill phase**: process the input prompt. All tokens are known, so attention can be computed in parallel. Computation is $O(n^2 d)$ where $n$ is prompt length. At large batch sizes and long prompts, this phase is compute-bound — GPU tensor cores are the limiting resource.

**Decode phase**: generate tokens one at a time. Each new token requires attending to all previous tokens (via the KV cache). Each decoding step reads the entire KV cache and model weights from GPU HBM — this is memory-bandwidth-bound. The GPU's tensor cores sit mostly idle.

The **Roofline model** captures this: a GPU's compute throughput divided by memory bandwidth gives the arithmetic intensity at which a kernel switches from memory-bound to compute-bound. For most LLMs at typical batch sizes, decoding falls well below this threshold — we're waiting for memory, not compute.

This is why batch size matters: increasing the batch size during decode amortizes the weight reads across more tokens, increasing arithmetic intensity. But batch size is limited by the KV cache memory available.

## KV Cache Mechanics

The KV cache avoids recomputing keys and values for previously seen tokens. Without it, generating token $n$ would require processing the entire context of length $n-1$ from scratch — $O(n^2)$ cumulative work for a sequence of length $n$.

With the KV cache:
1. Prefill: process full prompt, save $K$ and $V$ for every token at every layer
2. Each decoding step: compute Q, K, V for the new token only; retrieve cached K, V from HBM; compute attention

**KV cache size** for a single sequence at context length $L$:

$$2 \times n_{\text{layers}} \times n_{\text{KV heads}} \times d_{\text{head}} \times L \times \text{bytes\_per\_value}$$

For Llama-3-70B (80 layers, 8 KV heads, 128 head dim, FP16):
- Per token: $2 \times 80 \times 8 \times 128 \times 2 = 327,680$ bytes = 0.32 MB
- At 1K tokens: 320 MB
- At 128K tokens: 40 GB — half the GPU memory of an 80GB A100

This is the fundamental tension in LLM serving: longer contexts consume more GPU memory, leaving less for batching multiple requests.

## PagedAttention: Virtual Memory for KV Cache

**vLLM's PagedAttention (Kwon et al., 2023)** solved the KV cache memory fragmentation problem using OS virtual memory concepts.

The problem: standard KV cache implementations pre-allocate contiguous memory for each request's maximum sequence length. A request with max 2048 tokens reserves 2048 slots even if it uses 100. Internal fragmentation wastes 90% of memory. Since different requests complete at different times, the memory becomes a patchwork of free and occupied blocks that are hard to reuse.

**PagedAttention** stores KV cache in fixed-size pages (blocks of 16 or 32 tokens). Each request's KV cache is a linked list of pages, not a contiguous buffer. Pages can be allocated from a free pool dynamically and returned when a request completes — just like OS page tables map virtual addresses to physical pages.

Benefits:
- **Near-zero fragmentation**: unused space per request is at most one block (partial last page)
- **Memory sharing**: prefix caching reuses pages for identical prompt prefixes across requests
- **Copy-on-write**: beam search can share the base sequence's KV pages and only copy when beams diverge

vLLM achieved **24× higher throughput** vs naive serving and **3.5× vs FasterTransformer** on Llama-13B at 99.9% request completion rate.

## Continuous Batching: Maximum GPU Utilization

**Static batching**: collect a batch of requests, run them together until all complete. The problem: requests have different output lengths. Short requests finish early but the GPU must wait for the longest request. GPU utilization drops as requests trickle out.

**Continuous batching (iteration-level scheduling, Yu et al. 2022)**: at every decode step, any request that has generated its `<eos>` token can be removed from the batch and a new request can be added. The batch is dynamic — it changes every iteration.

Implementation: the serving system maintains a queue of pending requests. After each decode iteration, it checks for completed requests, removes them, and fills their slots from the queue. The KV cache slots of completed requests are immediately reused.

Effect: GPU utilization stays high throughout serving. Instead of 80% utilization dropping to 40% as the batch thins out, it stays at 80%+ continuously. **36.9× throughput improvement** measured by Yu et al. versus naive static batching.

Continuous batching is now the default in all production serving systems: vLLM, TGI (Text Generation Inference), TensorRT-LLM, LitServe.

<Callout type="info" title="Prefill-Decode Disaggregation">
For very high-throughput systems, prefill and decode can run on separate GPU clusters. A "prefill worker" runs all the compute-intensive prefill operations and sends the resulting KV cache to a "decode worker" which handles the memory-bandwidth-bound decoding. This separates the two phases' resource needs: prefill workers can be batched with many short prompts for compute efficiency; decode workers can serve long-running generation at high throughput. Used at production scale at companies like Alibaba and ByteDance.
</Callout>

## Speculative Decoding

**Speculative decoding (Leviathan et al., 2023; Chen et al., 2023)** exploits the observation that decode is memory-bound: the GPU is idle most of the time. It uses a small draft model to "speculate" multiple tokens ahead, which the large model then verifies in parallel.

**Algorithm**:
1. Small draft model generates $k$ tokens (e.g., $k=5$) autoregressively
2. Large target model processes all $k$ tokens in **one forward pass** (parallel prefill)
3. Compare target model probabilities to draft model predictions using rejection sampling
4. Accept tokens where the draft was good; reject at the first divergence
5. Start again from the divergence point

**Key insight**: the target model's parallel verification pass costs only marginally more than a single decode step (since prefill is compute-efficient), but if all $k$ tokens are accepted, you've generated $k$ tokens for roughly the cost of 1. Typical acceptance rate: 60–80%. Average tokens generated per target model step: ~3–4.

**Speedup**: 2–3× latency reduction at same output quality (rejection sampling guarantees the same distribution as the target model alone). The small draft model only needs to be compatible with the target model — typically a 1.3B model for a 70B target.

Variants: **Medusa** (multiple draft heads on the target model itself, no separate model), **EAGLE** (uses target model's hidden states for better draft quality), **LOOKAHEAD** (Jacobi decoding based).

## Quantization for Memory and Speed

**Post-training quantization (PTQ)** converts FP16 weights to lower precision without retraining.

**INT8 quantization**: weights in 8-bit integers, activations in FP16. 2× memory reduction. On GPUs with INT8 tensor cores (A100, H100), can be 2× faster for decode. Used in `bitsandbytes`, LLM.int8().

**GPTQ (Frantar et al., 2022)**: second-order (Hessian-based) weight quantization. Compensates for quantization error by adjusting remaining weights using the inverse Hessian. 4-bit with GPTQ achieves quality close to FP16 on most benchmarks. Supports 3-bit and even 2-bit with higher quality degradation.

**AWQ (Activation-aware Weight Quantization)**: identifies the 1% of weight channels most important to activations (high activation magnitude) and preserves those at higher precision, aggressively quantizing the rest. Better quality than GPTQ at the same bit width.

**FP8 training and inference (H100)**: NVIDIA H100 GPUs have native FP8 tensor cores — 2× faster than FP16, same memory as INT8. DeepSeek used FP8 mixed-precision training for its V2 and V3 models, cited as a major cost reduction contributor.

## Tensor and Pipeline Parallelism

When a model doesn't fit on a single GPU, it must be distributed:

**Tensor parallelism (Megatron-LM)**: split each weight matrix across GPUs along rows or columns. Each GPU holds a slice of each layer. Each forward pass requires an AllReduce to combine partial results. Communication overhead: 2 AllReduces per transformer block. Works well within a single node (fast NVLink). Typical: 8-way tensor parallel within a node.

**Pipeline parallelism**: assign consecutive layers to consecutive GPUs. GPU 0 runs layers 1–20, GPU 1 runs layers 21–40. Communication: small activation tensors passed between stage boundaries. Works well across nodes (slow infiniband). Micro-batching hides pipeline bubbles.

For 70B models in production: 8-way tensor parallel within a node handles serving efficiently. For 405B+ models: combine 8-way TP within nodes with 4-way PP across nodes.
