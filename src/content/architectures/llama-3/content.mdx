# LLaMA 3

## 1. Overview
LLaMA 3, released by Meta in April 2024, is a testament to the staggering power of extreme data scaling and optimization. While LLaMA 2 established the open-source baseline by training on 2 Trillion tokens, LLaMA 3 shattered it by training on an astronomical **15 Trillion tokens**. Meta released initial sizes at 8B and 70B parameters, and later a colossal 405B dense model. The 8B version is a marvel of "inference-optimal" scaling: by heavily over-training a relatively small parameter model far past the Chinchilla optimal point, Meta created a model that fits on a standard laptop GPU yet performs at the level of models 10 times its size (like GPT-3.5 and early Claude 3 variants). Furthermore, LLaMA 3 vastly improved its coding, reasoning, and multilingual capabilities by introducing a massive new 128,000-token vocabulary (using tiktoken) and native Grouped Query Attention (GQA) across all sizes. It stands as a definitive proof that we have not yet hit the ceiling of what dense transformer architectures can achieve when fed unprecedented volumes of high-quality data.

:::tip
LLaMA 3 8B is the ultimate model for local, edge, and mobile deployment. Because it was trained on 15T tokens, its reasoning per parameter is unprecedented. You can run the 4-bit quantized version smoothly on an 8GB VRAM consumer GPU and achieve production-grade conversational AI.
:::

## 2. Historical Context
By early 2024, the open-source community was heavily relying on LLaMA 2, but proprietary models (GPT-4, Claude 3 Opus) were pulling far ahead in complex coding and mathematical reasoning. Furthermore, smaller, highly optimized models from competitors like Mistral (Mistral 7B) had proven that LLaMA 2 7B was severely under-trained and inefficient. Meta needed to reclaim the open-source crown. Instead of inventing a wildly new architecture (like Mixture of Experts), they placed a massive bet on pure data scale and data quality. They built two custom 24,000 GPU clusters and spent months rigorously curating 15 Trillion tokens of data—including 4x more coding data and 30x more non-English text than LLaMA 2. When they released LLaMA 3 8B and 70B, the models immediately topped the open-source leaderboards, rivaling closed-source frontier models. The release cemented Meta's strategy: brute-force dense scaling, perfected data pipelines, and a commitment to open weights to drive the industry standard.

## 3. Problem It Solves
LLaMA 3 solves the **Small Model Stupidity** problem and the **Vocabulary Inefficiency** problem. Historically, models under 10B parameters were considered "toys"—good for simple chat, but incapable of holding strict logical context or writing complex Python scripts. By training the 8B model on 15 Trillion tokens, Meta solved this. They created an "inference-optimal" model, meaning they spent massive amounts of money during training so that millions of users could run a highly intelligent model incredibly cheaply during inference. Secondly, LLaMA 2 used a small 32,000 token vocabulary, which was terrible for non-English languages and code; it would fragment words into too many tokens, wasting the context window and slowing down generation. LLaMA 3 solved this by moving to a 128,000 token vocabulary based on `tiktoken`, compressing text much more efficiently. This allows the model to "see" further back in a conversation and generate code significantly faster.

**Components:**
- `Tiktoken Vocabulary`: Expanded from 32K to 128K. It drastically improves character-to-token compression, especially for code formatting (spaces/tabs) and multilingual characters.
- `LLaMA 3 Decoder`: Structurally almost identical to LLaMA 2. The magic is in the training duration and data quality, not new layer types.
- `Grouped Query Attention (GQA)`: Unlike LLaMA 2 (which only used GQA in the 70B model), LLaMA 3 uses GQA natively across *all* sizes, including the 8B model, ensuring blazing fast inference speeds and tiny KV-cache memory footprints everywhere.
- `RoPE (High Base)`: The base frequency of the Rotary Positional Embeddings was vastly increased to support a native 128,000-token context window out of the box, matching GPT-4 Turbo.

## 5. Layer-by-Layer Breakdown
Meta explicitly stated their goal was to avoid complex architectural novelties and rely on proven, stable mechanisms to guarantee training scaling.
1. **Tokenizer (Tiktoken)**: The 128K vocabulary requires a massive embedding table, but yields up to 15% better compression on English text and vastly more on code/foreign languages compared to LLaMA 2.
2. **Context Window**: 128K native context. To support this without losing fine-grained detail, the RoPE base frequency was increased to $500,000$ (compared to $10,000$ in standard models), allowing the model to distinguish between tokens that are tens of thousands of positions apart.
3. **RMSNorm & SwiGLU**: Retained unchanged from LLaMA 2.
4. **Grouped Query Attention (GQA)**: Standardized across the entire fleet. The 8B model uses 32 Query heads and 8 Key/Value heads. This 4-to-1 grouping is the secret to why the 8B model generates text so quickly on low-end hardware.
5. **Scale (8B)**: 32 layers, hidden dimension of 4096.
6. **Alignment**: Post-training heavily utilized DPO (Direct Preference Optimization) alongside standard PPO to align the chat variants, drastically reducing the annoying "refusal bias" that plagued LLaMA 2.

:::warning
Because of the massive 128K vocabulary, the embedding matrix and the final output classification head consume a significant portion of the parameters in the 8B model. While it says "8B", roughly 1 Billion parameters are tied up just in the vocabulary mapping.
:::

## 6. Tensor Flow Walkthrough
Let's trace the memory efficiency of the 8B model during a long-context GQA inference step.
- `B`: Batch size (e.g., 1)
- `T`: Context length (e.g., 100,000 tokens)
- `D`: Hidden dim (4096)
- `H`: Query heads (32)
- `G`: KV heads (8)
- `D_h`: Head dim (128)

1. **The KV Cache Problem**:
   - If using standard MHA, the KV cache requires storing 32 heads of size 128 for 100,000 tokens.
   - Cache size per layer = $2 \times 100000 \times 32 \times 128$ floats = ~3.2 GB.
   - Total for 32 layers = ~102 GB just for the cache!
2. **GQA to the Rescue**:
   - Because LLaMA 3 uses GQA with $G=8$, it only stores 8 heads.
   - Cache size per layer = $2 \times 100000 \times 8 \times 128$ floats = ~800 MB.
   - Total for 32 layers = ~25 GB.
3. **Execution**:
   - The new token generates $Q$ (32 heads), and $K, V$ (8 heads).
   - $K, V$ are appended to the highly compressed 25 GB cache.
   - The 8 KV heads are broadcast (repeated 4 times each) to match the 32 $Q$ heads during the attention dot-product.
   - `Context = Softmax(Q @ K_repeated^T) @ V_repeated`.

## 7. Mathematical Foundations
LLaMA 3 is the ultimate demonstration of pushing past the Chinchilla scaling limits into the realm of **Inference-Optimal Scaling**.

**Chinchilla vs Inference-Optimal:**
Recall that Chinchilla dictates training 20 tokens per parameter. For an 8 Billion parameter model, the compute-optimal dataset is roughly 160 Billion tokens. Training past this point yields mathematically diminishing returns on the training loss per dollar spent on compute.
However, Meta's goal was not to optimize training compute; their goal was to optimize *inference compute* for the end-user.
By training the 8B model on 15 Trillion tokens (nearly 100x the Chinchilla recommendation), Meta absorbed a massive financial penalty during training. They spent millions of dollars forcing the gradient descent algorithm to squeeze every last drop of semantic understanding into those 8 Billion weights.
The mathematical result is a model that is vastly "smarter" than an 8B model should theoretically be. When a user downloads LLaMA 3 8B, they get the intelligence of a much larger model, but they only pay the inference cost ($O(N)$ memory and FLOPs) of an 8B model. This mathematical trade-off (expensive training for cheap inference) defines the modern open-source AI strategy.

## 8. Training Procedure
1. **Data Curation**: The 15T token dataset required unprecedented engineering. Meta built custom data pipelines utilizing heuristic filters, NSFW filters, semantic deduplication, and text classifiers to identify high-quality text. Crucially, they used the massive LLaMA 2 70B model to generate the training data for the classifiers that filtered the data for LLaMA 3.
2. **Annealing**: Toward the end of the massive training run, they dropped the learning rate to zero and trained on highly specialized, ultra-high-quality data (like math and code) for the final few billion tokens. This "annealing" phase forces the model to lock in complex reasoning capabilities right before training ends.
3. **DPO Alignment**: While LLaMA 2 relied heavily on PPO (which requires training a separate Reward Model), LLaMA 3 heavily integrated DPO (Direct Preference Optimization). DPO simplifies RLHF by optimizing the policy model directly on human preference data (Winner vs Loser responses) using binary cross-entropy, eliminating the need for a volatile Reward Model and making the alignment phase much more stable.

## 9. PyTorch Implementation
Here is a conceptual implementation of how Direct Preference Optimization (DPO) calculates the loss to align LLaMA-3, simplifying the RLHF process.

```python
import torch
import torch.nn.functional as F

def dpo_loss(
    policy_chosen_logps: torch.Tensor,
    policy_rejected_logps: torch.Tensor,
    reference_chosen_logps: torch.Tensor,
    reference_rejected_logps: torch.Tensor,
    beta: float = 0.1
) -> torch.Tensor:
    """
    Direct Preference Optimization (DPO) Loss.
    Aligns the model without needing a separate Reward Model.
    
    Args:
        policy_*: Log probabilities from the model currently being trained.
        reference_*: Log probabilities from the frozen base model (SFT).
        beta: Temperature parameter controlling deviation from the reference model.
    """
    # 1. Calculate the implicit reward for the chosen (winning) response
    # Reward is defined as the difference in log probs scaled by beta
    chosen_reward = beta * (policy_chosen_logps - reference_chosen_logps)
    
    # 2. Calculate the implicit reward for the rejected (losing) response
    rejected_reward = beta * (policy_rejected_logps - reference_rejected_logps)
    
    # 3. Calculate the difference in implicit rewards
    # We want the chosen reward to be much higher than the rejected reward
    reward_diff = chosen_reward - rejected_reward
    
    # 4. Apply Bradley-Terry model loss (Negative Log Sigmoid)
    # If chosen_reward >> rejected_reward, loss approaches 0.
    loss = -F.logsigmoid(reward_diff).mean()
    
    return loss

# --- Verification Test ---
if __name__ == "__main__":
    BATCH_SIZE = 4
    BETA = 0.1
    
    # Simulated log probabilities (sum of log probs over a generated sequence)
    # For the reference (frozen) model
    ref_chosen = torch.tensor([-10.0, -12.0, -9.0, -11.0])
    ref_reject = torch.tensor([-10.5, -11.0, -9.5, -10.0])
    
    # For the policy model (currently training)
    # Scenario: The policy model assigns higher probability to the chosen response
    # and lower probability to the rejected response, compared to the reference model.
    pol_chosen = torch.tensor([-8.0, -10.0, -7.0, -9.0])
    pol_reject = torch.tensor([-12.0, -13.0, -11.0, -12.0])
    
    loss = dpo_loss(pol_chosen, pol_reject, ref_chosen, ref_reject, beta=BETA)
    
    assert loss.dim() == 0, "Loss must be a scalar"
    print(f"Test passed! DPO Loss calculated: {loss.item():.4f}")
    # The loss should be small, as the policy is moving in the correct direction.
```

## 10. Strengths
LLaMA 3's primary strength is its devastating efficiency. The 8B model punches wildly above its weight class, routinely beating models in the 30B-70B range on benchmarks like MMLU and HumanEval. This extreme inference-optimality makes it the perfect candidate for local deployment, mobile apps, and edge computing where VRAM is scarce. Secondly, its updated 128K tiktoken vocabulary completely resolved LLaMA 2's struggles with non-English languages and code formatting, making it a truly global and capable developer tool. Furthermore, the alignment process was vastly improved; LLaMA 3 Chat models are helpful, witty, and suffer from very low false-refusal rates compared to their highly censored predecessors. Finally, the native inclusion of GQA across all sizes and a 128K context window means the models are built from day one to handle massive RAG (Retrieval-Augmented Generation) workloads efficiently.

## 11. Weaknesses
Because LLaMA 3 8B is pushed so far past the Chinchilla scaling limits, it is mathematically "saturated." If you attempt to continually pre-train or heavily fine-tune the 8B model on massive new datasets, it suffers from catastrophic forgetting much faster than an under-trained model would, because its parameter capacity is already completely full of information. Secondly, the massive 128K vocabulary comes at a cost: the embedding matrix and output projection head take up a massive chunk of parameters. In the 8B model, the "brain" (transformer layers) is actually smaller than one might expect, as so much parameter budget is tied up in the vocabulary mapping. Finally, while the 405B model is a marvel of open-source engineering, it is practically unusable for the average developer, requiring server racks of H100 GPUs just to load into memory, highlighting the limits of dense architectures at the frontier scale.

## 12. Research Evolution
LLaMA 3 is the pinnacle of the dense Transformer era. It proved that the original architecture from 2017 is still fully capable of achieving frontier-level intelligence, provided you have the engineering talent to curate 15 Trillion tokens and the financial backing to run 24,000 GPUs continuously. It decisively ended the debate on inference-optimal scaling; the industry now universally agrees that over-training small models is the optimal strategy for commercial deployment. However, the release of the massive 405B dense model also highlighted a dead end. Running a 405B dense model is too expensive. This realization pushed the broader industry (and likely Meta's future models) toward Sparse Architectures like Mixture of Experts (MoE), which provide the capacity of a 400B model with the inference cost of a 50B model.

## 13. Interview Questions
**Q1: What does it mean that LLaMA 3 8B is "inference-optimal" rather than "compute-optimal"?**
**A1:** "Compute-optimal" (Chinchilla) means training the smartest model possible for a fixed training budget. For an 8B model, that means training on ~160B tokens. "Inference-optimal" ignores the training budget. Meta trained the 8B model on 15 Trillion tokens, wasting millions of dollars in training compute to ensure the final model is as smart as possible, so that end-users enjoy high intelligence with very low inference costs.

**Q2: Why did LLaMA 3 switch from a 32K vocabulary to a 128K vocabulary?**
**A2:** The 32K vocabulary was inefficient for code (many spaces/tabs) and non-English languages (splitting foreign characters into meaningless bytes). The 128K vocabulary compresses text much better. Because a single token now holds more information, the model can process long foreign documents or complex code scripts much faster and with better contextual understanding.

**Q3: How does Direct Preference Optimization (DPO) simplify the alignment process compared to PPO?**
**A3:** PPO (used in LLaMA 2) requires a highly complex, unstable pipeline where you must train a separate Reward Model, and then use an RL algorithm to optimize the policy model against it. DPO mathematically maps the reward function directly into the policy model's loss function (using binary cross-entropy on winning/losing responses), eliminating the need for the Reward Model entirely.

**Q4: Why does LLaMA 3 8B use Grouped Query Attention (GQA) when LLaMA 2 7B only used standard Multi-Head Attention (MHA)?**
**A4:** LLaMA 3 targets massive context windows (128,000 tokens). If an 8B model used standard MHA for 128K tokens, the KV-cache would consume more VRAM than the model weights themselves, crashing consumer GPUs. By natively standardizing GQA across all sizes, Meta ensured that the 8B model could process massive documents without running out of memory.

**Q5: What is "annealing" during the training of an LLM?**
**A5:** Annealing is a phase at the very end of pre-training where the learning rate is decayed to near-zero, and the model is fed a highly curated, ultra-high-quality subset of data (like complex math, code, and logic puzzles). This forces the model to solidify its highest-level reasoning capabilities right before the training run concludes.
